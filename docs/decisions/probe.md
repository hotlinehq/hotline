# Probe decisions (Peter, 2026-11-21 and 2026-11-22)

From the spike on finding out why a connection to a vendor fails, in the project thread. Report, lab test and requirements: `connection-diagnosis/report.md` and `connection-diagnosis/probe-slice-1/requirements.md` in the project files. What the proxy sends: [docs/otel-export.md](../otel-export.md), "Probes".

1. A **probe** is a check of a vendor's host and port after calls to it fail to connect. It finds out which side of the connection the problem is on and sends one record and one trace. It is not a health check (that is `/livez` and `/readyz`, and later the vendor health check, which runs on a schedule and is off by default). The word was chosen over "diagnosis" and "connection probe".
2. What starts one: a call with `error.type` `dns_error`, `dns_timeout`, `connection_refused`, `connection_timeout`, `destination_unavailable`, `tls_certificate_error` or `tls_protocol_error`. Not `destination_ip_prohibited` (the proxy's own rule), and not a failure after the connection worked.
3. One probe per host and port, shared by every integration and api calling it, so thousands of failing calls make one probe. At most one runs for a host and port at a time.
4. Backoff: the first failure probes at once; while calls keep failing the next is due after `backoff.first` (1m), then the wait doubles up to `backoff.longest` (15m). The schedule ends when a call to the host and port connects, or when none has failed for `backoff.quietAfter` (15m). The next probe starts only when a call failed since the last one, so a vendor nobody calls is not probed.
5. Probes run on 2 workers, off the call path. The call gets its `502` or `504` at once, as before.
6. Slice 1 asks three questions with the code calls already use (the same resolver, dialer, internal address guard and certificate authorities): `name_resolves`, `port_accepts_us` and `tls_works`, each `yes`, `no` or `not_checked`, with evidence lines. Each step waits at most `probeTimeout` (2s). It sends no HTTP request. Questions after the first "no" are `not_checked` and have no span.
7. `hotline.probe.side` is the side of the first "no": `our_side`, `between`, `vendor_side`, or `none`. The verdicts are `dns_name_not_found`, `dns_failed`, `refused_by_vendor`, `no_answer`, `unreachable`, `tls_cut_by_vendor`, `tls_certificate_failed`, `tls_failed` and `reachable_now`.
8. The record has event name `hotline.probe`, severity WARN (INFO for `reachable_now`), and the verdict as a plain sentence in its body. It goes into the ledger on its own chain, `hotline.probe`, which a reload keeps, and `hotline-proxy verify` checks it.
9. The trace: a root span `probe`, linked to the call span of the failed call that made it due, and one span per question asked.
10. Every call record links to the latest probe of its host and port while the schedule runs, failed or not: `hotline.probe.record_hash` and `hotline.probe.trace_id`. A failed call also gets `hotline.probe.side`, `hotline.probe.verdict` and `hotline.probe.time`. With no probe finished, or once the vendor recovered, nothing is attached (Peter, 2026-11-22).
11. Config, per api only, on by default (Peter, Q2): `probe: { enabled, backoff: { first, longest, quietAfter }, probeTimeout }`. A wait that is zero or less, or `first` longer than `longest`, makes the config invalid. An unknown setting, and a `probe` section on an integration, is a warning and is ignored, as for every other setting. Hosts outside the apis use the defaults.
12. Two apis on one host: the more careful setting wins: off when either is off, and the longer of each wait.
13. A reload keeps each schedule. New settings apply from the next wait: the wait already set runs out first. Turning the probe off ends the schedule at the next failure or due time.
14. The console prints one line: the time, `PROBE`, the host and port, the side and the sentence.
15. The file exporter writes the body as `body`, and a span's links as `links`, each with `trace_id` and `span_id`. The ledger's trace hash does not cover links yet.
16. The shop example on Floci ends with a call to SQS on a closed port, on purpose, so a probe shows in Grafana Cloud.
17. Later slices: the TCP and UDP path traces and ping (`path_reaches_vendor`, `host_up`), then our public IP, `egressIPLookup`, `allowedEgressIPs` and the control address, then the vendor health check.
