# WebSocket decisions (Peter, 2026-11-18)

From the WebSocket interview in the project thread. Requirements: `shop-assistant/requirements.md` in the project files. What the proxy sends: [docs/otel-export.md](../otel-export.md), "WebSocket sessions".

1. Two milestones (Q1): first see and prove what both sides said, then check messages against an AsyncAPI document, count them and put the results on the session record. *Replaced by items 15 and 16 (2026-11-19): messages are listed in the vendor's OpenAPI spec, not an AsyncAPI document, and each gets a record of its own.*
2. Milestone 1 counts only bytes (Q2): per direction, the WebSocket's frames after the `101` as they passed, compressed or not, without TLS; and how long the session was open. No frames are read.
3. Counting (Q3): the opening call counts once in `hotline.requests`, with status 101. The session is not counted, as a `CONNECT` tunnel that opens fine is not. Message counts come with milestone 2, in a counter of their own. *Replaced by item 26 (2026-11-19): no message counter.*
4. The opening call and the session are two records in one trace (Q5): the call is recorded when the `101` reaches the app, with no response body and its time ending there; the session gets its own record, `hotline.websocket.session`, and its own span, `websocket session`, a child of `hotline call` from the `101` to the end.
5. Each direction is hashed for the ledger, keyed with the session's trace and span ids, under `hotline.websocket.from_app.hash` and `hotline.websocket.from_vendor.hash`.
6. A session still open when the proxy stops is ended and recorded within the stop's time. *Since program item 8, a stop lets it run; four fifths into the time left once the drain delay ends, it is cut and recorded.*
7. Who ended the session and its close code are left to milestone 2, read from the close message itself (Q10). *Settled by item 28 (2026-11-19).* The proxy can see only which connection closed first, which in a WebSocket is nearly always the vendor's.
8. The exporters tell a session record from a call record by `export.Call.Event`, empty for a call (Q14). Only a call counts in `hotline.requests`, and the console shows a session in two lines of its own. Revisit if a session record needs things a call never has inside the sink, such as its own queue; then a separate type.
9. The forwarder tells the handler when the `101` has reached the app, with the optional `forward.Switcher` (Q15; [forwarder.md](forwarder.md), item 8).
10. Revisit if a WebSocket must be checked over HTTP/2, or plain `ws://` on the transparent listeners: both are left for later.

## The shop assistant (Peter, 2026-11-18)

The example that shows milestone 1 at work, in `examples/aws-shop`. Requirements: `shop-assistant/requirements.md` in the project files.

11. A fourth app, `assistant`, integration `shop-assistant`: it talks to Gemini Live through Google's Go SDK, text only, with one tool, `orderStatus(orderId)`, which reads the order from the DynamoDB `orders` table. It waits for the turn that holds the answer after a tool call. Settings: `GEMINI_API_KEY`, `GEMINI_MODEL`, `GEMINI_BASE_URL`.
12. The opening call is checked against [specs/google/gemini-live](../../specs/google/gemini-live/), whose security section names `x-goog-api-key`, so the key is in no record, span or log, even with content: full. The Floci run fails if it finds the key in its records or log.
13. Gemini Live is played by aimock (a scripted fake of AI vendors, `ghcr.io/copilotkit/aimock`, pinned by digest) behind a small TLS front (socat), reached over `wss://` through `CONNECT`, which Hotline opens with a test certificate authority made for the run.
14. The assistant runs only in the Floci workflow, on Linux (Q16). The example needs no run against real AWS or real Gemini; aimock and its front start in `floci/up.sh`. Revisit if the story must run against real AWS or real Gemini, or on a Mac.

## Messages checked against the spec (Peter, 2026-11-19)

Slice 2 ("milestone 2" above), decided one question at a time (Q1 to Q27 of the spike). Spike, review and requirements: `websocket-milestone-2/` in the project files. What the proxy sends: [docs/otel-export.md](../otel-export.md), "WebSocket messages". The marks: [docs/spec-marks.md](../spec-marks.md).

15. Messages are listed in the vendor's OpenAPI spec (Q25): the operation that answers `101` carries `x-hotline-messages`, with `fromApp` and `fromVendor` lists of `$ref`s to `components/schemas`. The spec loader reads it, and overlays apply as for bodies. A session uses the messages of the route its opening call matched; a route without the mark gets byte counts only. No AsyncAPI document and no new config key. *Changed by item 32 (2026-11-21): still one OpenAPI file and no config key, but the messages are written in AsyncAPI 3's shapes under `x-async-api`.*
16. A record per message (Q1), `hotline.websocket.message`, in the ledger like any record, and a span per message (Q21, Q22), `websocket message` under `websocket session`, sent as soon as the message ends. The record carries that span's id, so trace id and span id name one message. Under the span, `message spec check`, and `wait for check worker` under that. No span for unpacking. Revisit if the load case shows the exporters can't keep up with a record and a span per audio chunk (Q1, requirement 20).
17. A message is named by `x-hotline-match: true` on fields of its schema (Q2, Q3). A field with a `const` must have that value; otherwise it must be there. A message with several marks needs all of them. No match: the message is `unknown`, gets its record and span, and is not checked.
18. Unclear marks refuse the spec (Q3): a message with no mark, a mark inside a list, or two messages of a side where one's marks are all among the other's (so every message matching the second matches the first). At start this stops the proxy; at reload the last good spec stays. When a message still matches two schemas whose marks differ, the first listed wins. *Since item 32, "first listed" means by operation name, then in the order each operation lists its messages.*
19. A message is read by its side's content type (Q23, Q25), `application/json` unless the side is written `{ contentType: ..., messages: [...] }`, whether it came as a text or a binary frame. A side whose content type is not JSON is not read: its messages are `unknown` with `hotline.schema.skipped=unsupported_content_type`. *Since item 32 the content type is AsyncAPI's: `contentType` on a message or `defaultContentType` beside the operations, with the same meaning; the messages of one side share one.*
20. The same checker, limits and reasons as call bodies (Q13, Q25): checked up to 2 MiB counted after unpacking, skipped as `body_too_large`, `overloaded` or `unsupported_content_type`, results capped at 20 with a total. A message from the app has its results under `hotline.schema.request.errors`, one from the vendor under `hotline.schema.response.errors`, as for a call's two sides.
21. `checks` gains `messages` (Q27), included when `checks` is left out. Left out of a list, messages still get records, spans, names and ids, but no check, no `hotline.schema.*` attribute and no copied fields, as for a body left out. An existing `checks` list checks no messages until `messages` is added.
22. Checks run beside the session in the same spec check line, capped by `specChecks.queueMemory` (Q7). A full line drops the oldest waiting checks as `overloaded`, never a byte of the session.
23. Both kinds of compression are read (Q5, Q6): when the `101` agrees to `permessage-deflate`, the proxy unpacks a copy of each message. Packing against earlier messages keeps the last 32 KB unpacked per direction (less when the `101` agreed a smaller window) for as long as the session is open. Every message is unpacked in order, even one whose check is dropped or that is over 2 MiB, so a dropped check loses only that message.
24. The copies waiting to be read share the line's memory (Q17, Q26). A wire's reader that is waiting takes a copy of any size, as a free worker takes a check; one that is behind holds its copies under `specChecks.queueMemory`, and waiting spec checks give way first. When a copy can't fit at all, the reading of that side stops for good: that message and every later one are recorded as `unknown` with `hotline.schema.skipped=overloaded`, and the session record names the first one in `hotline.websocket.unread_from_index`. Frames the proxy can't read stop that side's reading the same way, with no reason.
25. Ids, not pairs (Q11, Q14, Q18): `x-hotline-id-tuple: <label>` goes on id fields, inside lists too, as Gemini's `functionCalls[].id`. The message record lists them as `label:value` under `hotline.websocket.ids`, up to 20 with `hotline.websocket.ids_total`. They are read in the step that names the message, which is never dropped. The proxy pairs nothing and keeps no ids per session. Token counts come only through `x-hotline-record` (Q9), copied as sent, never added up. *Changed by items 34 to 36 (2026-11-21): `x-hotline-id-tuple`, `hotline.websocket.ids` and `ids_total` are gone; each message carries one correlation id instead. "The proxy pairs nothing and keeps no ids per session" still stands (item 36).*
26. No message counter (Q16): `hotline.requests` stays for calls only; the message records are the count. Replaces item 3's counter.
27. The message's place: `hotline.websocket.message.index` (1, 2, 3 in the order their last bytes passed, both directions together), and its direction, `from_app` or `from_vendor` (Q20).
28. How the session ended (Q7), on the session record and span: `hotline.websocket.close.from` (`app` or `vendor`), `hotline.websocket.close.code` and `hotline.websocket.close.reason` of the first close message; or `close.from` `none` and `hotline.websocket.closed_first`, the side whose connection closed first. Only for a session whose route lists its messages, since only those are read.
29. Pings and pongs get no record and no span (Q24); the session record counts them per direction, as `hotline.websocket.from_app.pings` and the like.
30. The console shows no line for a message: a session may send many a second. It still shows the session's two lines.
31. The load case (Q12, requirement 19) is an xk6 extension on `coder/websocket`, since stock k6's `gorilla/websocket` packs each message alone only. Built (2026-11-19): `load/k6ws` adds `k6/x/hotline-live` to k6, `load/live` runs one Gemini Live session (40 ms audio chunks, 25 messages a second each way, a tool call every 25 chunks), and the workflow builds k6 v1.3.0 with it by xk6 v1.5.1 instead of downloading k6. `make load` runs it plain at 20, 50 and 100 sessions, and packed alone and against earlier messages at 50. Detail: [load/README.md](../../load/README.md). Requirement 20 is met: on the load runner, 100 sessions gave 5,200 message records and 15,700 spans a second with none skipped (run 66, 2026-11-19). That run's profile showed 24 to 29 KB handed out per 2 KB message; naming now reads only the fields the marks name, and the window of earlier bytes is kept in one buffer per session, which halved it (2026-11-20).

## AsyncAPI's shapes in the same file (Peter, 2026-11-21)

Decided one question at a time (Q1 to Q9) in the project thread. Requirements and worked examples: `asyncapi-shapes/requirements.md` and `asyncapi-shapes/pairing-examples.md` in the project files. The marks: [docs/spec-marks.md](../spec-marks.md), "x-async-api". What the proxy sends: [docs/otel-export.md](../otel-export.md), "WebSocket messages".

32. One spec file per vendor stays (item 15), but its messages and operations are written as in AsyncAPI 3, with `reply` and `correlationId` (Q1). Hotline's own WebSocket marks go where AsyncAPI has a word for the same thing: `action` replaces `fromApp` and `fromVendor`, `contentType` replaces the side's `{ contentType, messages }`. Every spec and test that used the old format moved. Revisit if customers arrive with full AsyncAPI files they want to use unchanged.
33. `x-hotline-match` stays (Q2), on fields of the message's payload schema, as items 17 and 18 say: it is cheap and still names a broken message. It is the one WebSocket mark left. Revisit if the specs people write almost always name messages by a top-level `const` or `required` field.
34. One `correlationId` per message, holding one value (Q3): `location: $message.payload#/...`, a JSON pointer to one field. A list is read at a fixed index (`/toolCall/functionCalls/0/id`), so a Gemini tool call with several calls records only the first id. `x-hotline-id-tuple` is gone. Revisit if business ids such as Kraken's `order_id` are needed next to the request id, or if vendors often send several ids in one message.
35. No combined span per pair (Q4). Each `websocket message` span carries its correlation id as `messaging.message.conversation_id`, so a query in the trace store groups a request with its replies. The first exception to "spans hold nothing the record holds" (otel-export.md, Signal 3). Revisit if trace queries by attribute turn out too slow or unsupported in the stores customers use.
36. No reply check in the proxy (Q5): it keeps nothing per session (item 25 stands on this). Wrong replies, replies to nothing and unanswered requests are found later in the data store. `reply` is checked when the spec loads, not enforced on traffic. No state machine per pair for now. Revisit if customers need these alerts in real time.
37. The operation's name goes on each message's span and record, `hotline.websocket.operation` (Q6), so the store can tell a wrong reply without the spec: same `conversation_id`, different operation. Kept even though the spec could supply it: the data store should work from the traces alone.
38. A message belongs to exactly one operation of its route (Q8). A reply that can't name its request, such as Kraken's failed subscribe, gets an operation of its own (`subscribeFailed`, sent by the vendor) instead of being shared by several `reply` lists.
39. Each message carries its role, `hotline.websocket.message.role`, inferred from the spec when it loads, with no new spec word (Q9): `request` (in an operation's `messages`, and the operation has a `reply`), `reply` (in an operation's `reply`), `answer` (has a `correlationId`, its operation has no reply, and it is in no reply) and `push` (none of these). On the span and the record, next to the operation. The store finds a wrong reply, an unanswered request and a reply to nothing by filtering on it. The docs warn that a business id used as a push's `correlationId` makes it an `answer`.
40. The key is `x-async-api` (Q7), with AsyncAPI's own names inside (`operations`, `messages`), on the operation that answers `101` and in `components/x-async-api/messages`. The `x-` prefix keeps the file valid OpenAPI, so vendors' specs still open in other tools and pass linters.
41. An HTTP call keeps one record for request and response (side decision). HTTP pairs them itself, splitting would make every reader join two records and double the ledger's volume, and calls without an answer already get a record. Revisit if the ledger must prove a request left even when the proxy dies before the response.
42. Spec rules, proposed with the requirements and built as written: `action` is `send` or `receive`; a message is a `$ref` to `components/x-async-api/messages`, and its `payload` a `$ref` to `components/schemas`; `correlationId.location` must start with `$message.payload#/` (`$message.header` refuses the spec, as a WebSocket message has no headers), and a text or number value is recorded, anything else nothing; `reply` takes `messages` only (`channel` and `address` refuse the spec); the messages of one side share one content type; `x-hotline-messages` and `x-hotline-id-tuple` refuse the spec with a pointer to the new words.
43. A second load case, Kraken's market data (Spot WebSocket v2), next to Gemini Live, with a fake Kraken and never the real API: shapes `kraken-plain`, `kraken-alone` and `kraken-context`, spec `specs/kraken/spot-websocket/v2.openapi.yaml`. Each session subscribes to the book of BTC/USD (a reply and a snapshot) and of an unknown pair (a `subscribeFailed`, so all four roles show), then pings every 40 ms; the fake answers each ping with a pong and a book update, and sends a heartbeat once a second. Its `make load` lines copy the Gemini case's session counts, packings and profile lines (20, 50 and 100 plain, 50 alone, 50 against earlier messages). Revisit the mix when real Kraken traffic shows a different shape, such as far more book updates than requests.
44. The WebSocket message scenarios (`websocket-messages.feature`) run against Kraken, not a made-up spec shaped like Gemini Live (Peter, 2026-11-21, Q1 to Q4 in the project files' `kraken-e2e/requirements.md`). Q1: market data and trading, for replies that repeat once per order, batches and refused orders. Q2: one shared spec, `specs/kraken/spot-websocket/v2.openapi.yaml`, written by a script from the unofficial AsyncAPI file, used by these scenarios and by the Kraken load case; scenarios that test a broken spec change only their own copy. Revisit if those edits keep breaking when the shared file changes. Q3: what Kraken has no message for (a request sent by the vendor, an id inside a list, an id path that stops at a plain value, and a route without `x-async-api`) runs in `websocket-tool-calls.feature`, with a small spec of its own; the Kraken spec is never bent for tests. Q4: the vendor is the step file's scripted vendor, sending Kraken messages; the load case keeps its own fake Kraken. Revisit if one fake could serve both. A field copied with `x-hotline-record` is now an add_order reply's order id (`kraken.order.id`), in place of Gemini's token count.
45. Traits on an x-async-api operation or message refuse the spec, saying to write what they add into the operation or message itself, and a `schemaFormat` on a message or its payload that is not JSON Schema (anything but AsyncAPI's, OpenAPI's or JSON Schema's own formats) refuses it too (Peter, 2026-11-21, roadmap M1). Both were ignored before, so what they said was silently lost. Revisit if a vendor spec we need shares its messages through traits: then merge them in.
