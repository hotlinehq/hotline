# Spec checks and shared apis decisions (Peter, 2026-10-29)

Full wording in [docs/proxy-spec-checks.md](../proxy-spec-checks.md).

1. Every part of a call is checked against the spec, not only the body: path, query, headers, cookies and body; in the response, status, headers and body.
2. Unknown query values are reported; unknown headers are ignored; extra body fields follow `additionalProperties`.
3. Each result is structured: `part`, `place`, `rule`, `expected`. Never a value from the call.
4. A content type the spec doesn't list, or a body where none is expected, is reported.
5. A response status the spec doesn't list (no `default`) is reported, and that response is not checked further.
6. At most 20 results per side, plus `errors_total` when more.
7. Common formats are checked (`date-time`, `date`, `email`, `uuid`, `uri`, `ipv4`, `ipv6`, `int32`, `int64`).
8. The login key from the security section must be present; its value is never read.
9. Only OpenAPI 3.1; `$ref` within the same file; OpenAPI query styles; Stripe's bracket form bodies.
10. A broken spec is a config problem: refused at start, by `validate` and on reload.
11. One spec is read once and shared by every integration that uses it.
12. The config names each vendor api once in a top-level `apis` section; integrations name the apis they use, and may change only `vendorTimeout`. `not-passed` keeps its settings on itself.
13. The JSON Schema engine sits behind a contract in `internal/spec/schemacheck.go` (Peter, 2026-11-05, reshaped 2026-11-06). spec reads and reasons about OpenAPI (routes, parameters, content types, `$ref`, x-hotline marks); an engine sees only JSON Schema 2020-12, never OpenAPI. `NewEngine` takes the shared schemas by name, with every `#/components/schemas/X` `$ref` turned into `#/$defs/X`, and compiles them once, so a shape used in many places, or one that names itself, is compiled once. `Engine` is a constructor: from a plain `RequestSpec` or `ResponseSpec` (parameters with where their value is, each body content with its schema, XML shape and marked fields) it builds a `RequestCheck` or `ResponseCheck`. spec keeps them in its route table and picks one per call. `Meta` gets the escaped path, raw query and `http.Header` as Go's server gives them and checks the parameters; `Body` gets the body's bytes, which content it was sent as and how to read it (JSON, XML or form), and does all the reading, checking and copying of marked fields in one pass. spec keeps what needs no schema: finding the route, the body gate (listed, required, content type, too large, streaming), login, unknown query names and marked headers. `internal/spec/read` holds readers any engine may use (XML by its shape, forms with brackets, parameter values, a copied value into a record's value). `internal/santhosh` is the engine today; `internal/config` hands `santhosh.NewEngine` to `spec.Parse`. Every engine runs the shared checks of `internal/spectest` (`spectest.Checks`) from its own tests, so all give the same reports; spec's own tests use fake engines. A schema is `map[string]any` for now; faster forms are left to later spikes.
14. santhosh reads a JSON body where it is, token by token with Go's `encoding/json/jsontext`, into Go data with numbers kept as `json.Number` (Peter, 2026-11-06), and picks the marked fields from that same value. `json.Decoder` first copied the whole body into a buffer of its own, about 300 KB of the 760 KB handed out per call on the 115 KB load test response. Like the old decoder it lets a name come twice (the last wins) and takes text that is not UTF-8. `jsontext` needs Go 1.27, or the `jsonv2` experiment. A JSON body with no schema is only checked to be JSON, with `json.Valid`.
15. An XML body is read straight into the Go data a JSON body would give, as Go's XML reader hands out its pieces, with no element tree in between (Peter, 2026-11-06). The reader runs raw (`RawToken`): no namespace is looked up, since only an element's name without its prefix is used, and the reader checks itself that each element is closed by its own name. A DOCTYPE is still refused. On the load test's 7 KB S3 listing this took the check from about 165 KB to 84 KB per call (about 21 to 10 times the body), and its time by about a fifth.
16. A body is read only 64 levels deep (security scan, 2026-11-18): a form field of more than 64 names, such as `metadata[a][a]…`, is `body $ form`, and XML nested more than 64 elements deep, the root counted, is `body $ xml`. A 2 MB body nested as deep as it could go took about 300 MB as a form and 180 MB as XML. JSON keeps the limit of Go's own reader, 10,000 levels.
17. A form body is always an object, even when every name in it is a number (found by fuzzing, 2026-11-18). Such a body, `0=x`, was turned into a list and stopped the proxy.

- Which parts run is a list, `checks`, on the api (Peter, 2026-11-08): `path`, `query`, `headers`, `cookies`, `body`, `status`, `response-headers`, `response-body`, and `messages` since 2026-11-19 ([websockets.md](websockets.md), item 21). Omitted means all, `[]` means the route only, an unknown name stops the start. No body copy is kept unless a body part is picked (a spec that names its action in the body keeps the request body). Detail: [docs/proxy-spec-checks.md](../proxy-spec-checks.md).

## Edge proxy: spec versions and webhooks (Peter, 2026-11-21; 18, 20 and 21 built)

Plan: [docs/spec-support/roadmap.md](../spec-support/roadmap.md).

18. The edge proxy reads OpenAPI 3.2 only, replacing item 9's "only OpenAPI 3.1". 3.1 and older are refused, since spec files are easy to rewrite to 3.2, and every spec in `specs/` and the tests moves to 3.2 in one go. Revisit if a 3.1 rule turns out to clash with 3.2, so a file can't be moved over by changing its version line alone. Checked against the 3.2.0 text and the OpenAPI Initiative's upgrade guide on 2026-11-21: 3.2 lists no breaking change from 3.1.
19. Webhook support is minimal: only the app calling the vendor, such as setting up webhook endpoints or posting to a vendor's webhook address, with the secret in that address never recorded. Calls from the vendor to the app are out of scope, so a spec's `webhooks` and `callbacks` sections are loaded and ignored.
20. New 3.2 parts the proxy can't check yet (`query`, `additionalOperations`, `in: querystring`, `itemSchema` and the rest) are skipped quietly, like any field the proxy does not know (Peter, 2026-11-21). The version is checked after overlays are applied, any `3.2.x` loads, and the refusal names the file, the version found and the fix: change the line to `openapi: 3.2.0`. Revisit if a vendor spec we need uses one of those parts and its calls are wrongly flagged or wrongly pass.
21. The base path is the path of the first servers address; its scheme and host are not parsed, since the config names the hosts (Peter, 2026-11-21, roadmap M1). Before, a variable in the host, such as `https://{region}.api.com/v1`, made the address unreadable and silently dropped `/v1`. A variable in the path stays in the route, like any path value. Revisit if a spec lists several servers with different base paths.

## Edge proxy: QUERY and discriminator (Peter, 2026-11-22, roadmap M3 part 1; built)

Requirements: `small-3.2-additions/requirements.md` in the project files.

22. A path's `query` operation is a route for the method `QUERY`, and each `additionalOperations` entry a route for the method its key names, written exactly as sent (method names are case sensitive). Both are checked like any route. An `additionalOperations` key that is one of the nine methods with a field of their own, in any case, or that is not a method name, refuses the spec. This replaces item 20 for those two parts.
23. A discriminator never changes pass or fail, as OpenAPI 3.2 says. When a `oneOf` or `anyOf` with a discriminator fails, the problems reported are those of the branch its field picks (by `mapping`, else the schema's name, else `defaultMapping`), with the usual keys and no new one; with no branch to pick, one problem `rule: discriminator` at the field, `expected` the values the spec gives, never the value sent (Q1, option B). Revisit if a real problem is hard to read without the branch's name, for example a discriminator on a whole body, where every place is just `$.x`: then add a `branch` key.
24. The engine stays free of OpenAPI: spec writes what a discriminator says as a note, `x-hotline-branch`, on the schema (`{property, choice, values: {value: branch position}, default}`, positions counted from 0 in the `oneOf` or `anyOf` that `choice` names), and the engine reads only that note (Q2, Peter, 2026-11-22: option A, which decomplect also picked). The note is described in the contract file, `schemacheck.go`; its positions are `json.Number`s, like every number in a schema, and a note the engine cannot read refuses the spec. Revisit if a second engine cannot read the note without OpenAPI knowledge, or if the JSON Schema library itself starts supporting the discriminator. A mapping to a schema the spec does not have, to one that is not a branch, or to another file, and a discriminator with no `propertyName`, refuse the spec. The `allOf` form and a discriminator with no choice beside it check nothing, as OpenAPI says, and are loaded and ignored. A mapped branch is meant only by its mapped values; a branch the mapping leaves out by its schema's name. A mapping value is looked up as a schema name first, so `Pet.v1` is a name. The engine relies on the JSON Schema library listing every failed branch's errors in the branches' order; revisit if a library upgrade changes that.

## Edge proxy: whole query string and cookie styles (Peter, 2026-11-23, roadmap M3 part 2; built)

Requirements: `small-3.2-additions/part-2-requirements.md` in the project files.

25. A parameter `in: querystring` is checked: the whole query string, read by the one media type of its `content` (a form for `application/x-www-form-urlencoded`, percent-decoded JSON for JSON types, percent-decoded text for any other). A finding inside it reads like one about a query parameter: part `query`, place `limit` or `filter.status`, and `$` for the whole value (Q1 = A, with decomplect's two fixes). A query string that cannot be read is one finding, `rule: querystring` at `$`. JSON and text are percent-decoded as a form is, with `+` a space, as browsers and Go's url package write it; a real plus is `%2B`. The engine reads the query string by the plain instruction `WholeQuery`, as it reads bodies by `Reads`; spec decides the instruction from the media type. Revisit if dashboards need query findings to read exactly like body findings (`$.limit`). Two querystring parameters, one beside `in: query` parameters, one without exactly one `content` entry, or an `x-hotline-redact` mark on one refuse the spec. This replaces item 20 for `in: querystring`.
26. One function gives the app's query: the query with the proxy's own names (a login key sent in the query, a word that picks the route) taken out, unless a query parameter has the name. The parameter checks and the check for unknown query names both use it. With a querystring parameter, no name is reported `not_in_spec`: its schema decides (before, every name was wrongly reported).
27. A query string read whole as JSON or text has no names, so the record's `url.full` shows its query as `REDACTED`. A form query string is redacted name by name, as before.
28. A cookie is read by its style, as OpenAPI says (Q3 = A): `form`, the default, percent-decodes the value; `cookie` takes it as written. A cookie name sent twice keeps every value (before, only the last). With explode on (the default), a list is the name repeated and an object is one cookie per property, taking only the schema's own properties so other cookies are never extra; with explode off, a list is `a,b` and an object `k1,v1,k2,v2`. Revisit if a user's spec relies on raw values without writing `style: cookie`. Reading styles stays in spec: the engine gets plain instructions (`Split`, `Spread`, `Decode`) and no OpenAPI names. An exploded object cookie whose schema names no properties refuses the spec, since its cookies could not be found.
29. Server `name` is not recorded for now (Q2): no spec in `specs/` gives a server a name, and `server.address` already says where a call went. An errorbar check (2026-11-23) confirmed both. Revisit when a spec gives servers a `name`, or lists two servers on one host with different paths, which also breaks item 21's base path.

## Edge proxy: second sweep of quiet gaps (Peter, 2026-11-23; built)

Requirements: `spec-gaps/second-sweep-requirements.md` in the project files. Roadmap M1 was already built, so Peter asked for a second sweep (Q1). Refusing everything the proxy skips was the first idea; Peter asked why refuse at all, and the answer was to check these parts instead and refuse only what OpenAPI itself forbids (Q2). None of the 40 spec files in the repository used any of them.

30. Every server's base path is read, replacing item 21's "first servers address". Each route is reachable under each top-level server's base path; a path's own `servers` replace the spec's for that path, and an operation's own replace its path's, as OpenAPI says. Servers with the same base path give one route, so Kraken's two servers load as before. The route template carries the base path the call matched. Revisit if two servers on one host need telling apart, which only server `name` (item 29) could do.
31. A parameter, or a response header, described with `content` is read by its one media type, as the querystring parameter is (item 25): a form for `application/x-www-form-urlencoded`, JSON for JSON types, text for any other. The value is checked against that media type's schema; a value that is not JSON, or not a form, is one finding, `rule: json` or `rule: form`, at the parameter, like a body. `schema` and `content` together, or `content` without exactly one media type, refuse the spec. The engine gets the plain instruction `ContentReads` (Peter, 2026-11-23: a `Reads` value, not the media type, so the rule for what counts as JSON lives in spec only).
32. Every parameter style OpenAPI 3.2 lists is read. `matrix` and `label` path values have their marks taken off (`;id=`, or `;` and then `id=` on each item when exploded, and `.`), and a value or item without its mark is one finding, `rule: prefix`, `expected` the mark. `spaceDelimited` and `pipeDelimited` query lists split on a space or `|`. Objects written in one value are read too: `R,100,G,200`, and `R=100,G=200` in an exploded path or header. Explode is on by default only for the form and cookie styles, as OpenAPI says (before, path and header values defaulted to on, which mattered to nothing until objects were read). Item 28's rule holds: the engine gets plain instructions and no style names. `Split` is renamed `ItemSeparator` and holds the text between items, and `ValuePrefix`, `ItemPrefix` and `ObjectWrittenNameEqualsValue` are new (Peter, 2026-11-23, names checked by decomplect's naming rule). A parameter described with `content` gets none of them, since no style applies to it. An empty matrix value written `;id` is reported as a missing prefix; no vendor writes it.
33. A style OpenAPI does not allow where a parameter lives refuses the spec, naming the styles it allows: path `simple`, `matrix`, `label`; query `form`, `spaceDelimited`, `pipeDelimited`, `deepObject`; header `simple`; cookie `form`, `cookie`. A response header may only be `simple`. A style that does not exist is refused the same way.
34. AsyncAPI bindings stay ignored: the WebSocket upgrade's query and headers are already checked by the route's OpenAPI parameters, so there is nothing left in them to check.
