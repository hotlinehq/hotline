# Spec checks and shared apis decisions (Peter, 2026-10-29)

Full wording in [docs/proxy-spec-checks.md](../proxy-spec-checks.md).

1. Every part of a call is checked against the spec, not only the body: path, query, headers, cookies and body; in the reply, status, headers and body.
2. Unknown query values are reported; unknown headers are ignored; extra body fields follow `additionalProperties`.
3. Each result is structured: `part`, `place`, `rule`, `expected`. Never a value from the call.
4. A content type the spec doesn't list, or a body where none is expected, is reported.
5. A reply status the spec doesn't list (no `default`) is reported, and that reply is not checked further.
6. At most 20 results per side, plus `errors_total` when more.
7. Common formats are checked (`date-time`, `date`, `email`, `uuid`, `uri`, `ipv4`, `ipv6`, `int32`, `int64`).
8. The login key from the security section must be present; its value is never read.
9. Only OpenAPI 3.1; `$ref` within the same file; OpenAPI query styles; Stripe's bracket form bodies.
10. A broken spec is a config problem: refused at start, by `validate` and on reload.
11. One spec is read once and shared by every integration that uses it.
12. The config names each vendor api once in a top-level `apis` section; integrations name the apis they use, and may change only `vendorTimeout`. `not-passed` keeps its settings on itself.
13. The JSON Schema engine sits behind a contract in `internal/spec/schemacheck.go` (Peter, 2026-11-05, reshaped 2026-11-06). spec reads and reasons about OpenAPI (routes, parameters, content types, `$ref`, x-hotline marks); an engine sees only JSON Schema 2020-12, never OpenAPI. `NewEngine` takes the shared schemas by name, with every `#/components/schemas/X` `$ref` turned into `#/$defs/X`, and compiles them once, so a shape used in many places, or one that names itself, is compiled once. `Engine` is a constructor: from a plain `RequestSpec` or `ResponseSpec` (parameters with where their value is, each body content with its schema, XML shape and marked fields) it builds a `RequestCheck` or `ResponseCheck`. spec keeps them in its route table and picks one per call. `Meta` gets the escaped path, raw query and `http.Header` as Go's server gives them and checks the parameters; `Body` gets the body's bytes, which content it was sent as and how to read it (JSON, XML or form), and does all the reading, checking and copying of marked fields in one pass. spec keeps what needs no schema: finding the route, the body gate (listed, required, content type, too large, streaming), login, unknown query names and marked headers. `internal/spec/read` holds readers any engine may use (XML by its shape, forms with brackets, parameter values, a copied value into a record's value). `internal/santhosh` is the engine today; `internal/config` hands `santhosh.NewEngine` to `spec.Parse`. Every engine runs the shared checks of `internal/spectest` (`spectest.Checks`) from its own tests, so all give the same reports; spec's own tests use fake engines. A schema is `map[string]any` for now; faster forms are left to later spikes.
14. santhosh reads a JSON body where it is, token by token with Go's `encoding/json/jsontext`, into Go data with numbers kept as `json.Number` (Peter, 2026-11-06), and picks the marked fields from that same value. `json.Decoder` first copied the whole body into a buffer of its own, about 300 KB of the 760 KB handed out per call on the 115 KB load test reply. Like the old decoder it lets a name come twice (the last wins) and takes text that is not UTF-8. `jsontext` needs Go 1.27, or the `jsonv2` experiment. A JSON body with no schema is only checked to be JSON, with `json.Valid`.
